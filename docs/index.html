X22

Our X server. A fork of XFree86, brought up to date for today's computers, with one goal: X that's as smooth as Wayland, without giving up a single X program.

Where it's at: it builds, draws on a real screen through the kernel without tearing, takes keyboards and mice, and has the X security fixes since 2008, font library included, so far in a virtual machine. Nothing to download yet. Progress goes in the news below as it happens.

This is all we're working on now. Chamesle itself is on hold for a while, so every hour goes here. More about that.

What is it?

X22 is an X server, the program that draws your windows and passes them your keyboard and mouse. Every Chamesle desktop runs on one (we believe in X). Right now that's X.Org's. X22 is going to be ours.

It starts from XFree86 4.8.0, the last XFree86 release, from December 2008. XFree86 was the X server on nearly every Linux and BSD PC through the 90s and into the 2000s, and this whole website is dressed like its old homepage. We took its source as it was released, checked against XFree86's own signatures, and we're carrying it on.

The name: it started out as X22, X for x86-64, the way XFree86 was free X for the 386 PCs of its day. That was a mouthful, so since November 10, 2026 it's X22. Same code, same plan.

News

November 10, 2026, night NEW
X-Resource 1.2. XFree86 4.8 had version 1.0 of this extension, which can count a program's windows and pixmaps but can't say which program a window belongs to. 1.2 can: ask about a window and the server tells you the process behind it, straight from the kernel, so a program can't lie about it. Window managers use that for swallowing, where a video or picture opened from a terminal takes the terminal's place until it's closed. Our dwm does that now, and on X22 it works with programs that don't put their process number on their windows themselves. The other half of 1.2, how much memory a program's pixmaps and windows take, is in too.
Two old bugs in the 1.0 part turned up on the way. One reply left out the last kind of resource while saying it was there, which threw the client off for everything after. And for a program with the other byte order, two requests swapped a 32-bit number as if it were 16 bits, so they asked about the wrong program. test/xres checks all of it, from both byte orders.
November 10, 2026, evening
New name, new address. X8664 is X22 now, and it has a site of its own here at x22.chamesle.org. The code moved to github.com/tortr-rs/x22 (the old address still takes you there), and the environment variables went with it: X22_KEYMAP and friends.
And the font library is done, which finishes step 7. The server reads font files itself, so every font bug is a server bug: BDF fonts with glyphs too big for the numbers that hold them, PCF fonts whose glyphs point past the end of the file, old compressed fonts that walk off a table, a font that's really a symlink to a file you shouldn't be able to read. All of those are fixed, along with the three font bugs X.Org announced this summer and one of June's, where a long font alias was copied onto the stack. Some things we turned off instead, the way X.Org did: talking to font servers, the Speedo and Type1 renderers, and two bitmap formats nobody has used in twenty years. test/fonts feeds the server some broken fonts and checks it's still there after.
One entry from June is still open: a bug in the screen saver's window that X.Org hasn't said much about yet. The rest of the list is in SECURITY.
November 10, 2026
X22 is what we work on now, full time. Chamesle is on hold for a while (more on the home page), and all of that time goes here instead.
Security, which is step 7. X.Org has put out a lot of security fixes since 2008, and most of them are for code we have too, so we went through every advisory about the X server since January 2008, one by one. That's 117 entries: 52 we fixed here by hand (the code has moved too far for X.Org's patches to just apply), 9 that XFree86 4.8 had already fixed its own way, and 49 for code we don't have, like XInput 2, GLX and Xwayland. Six are left, nearly all in the font library, which is next. The whole list, with what we did about each one, is in SECURITY.
One fix covers a lot of them at once: the code that reads requests from clients with the other byte order now checks a request is long enough before it touches it. That was 382 places in 38 files.
Testing the SYNC fixes turned up a bug XFree86 had all along: one bad request about an alarm and the server would spin forever the next time that alarm went off, so any program could freeze your screen. Two more in the same code freed an alarm twice, or while something still pointed at it. All three are fixed, and test/sync checks for them now.
November 8, 2026, 8 pm
Mice and touchpads go through libinput now, like keyboards already did through the kernel. Before, the server read /dev/input/mice, where the kernel makes every pointer look like a PS/2 mouse from the nineties: a touchpad moved the pointer and that was all. With libinput you get tap to click, two finger scrolling, palm detection and the rest, set up the way every other desktop sets them up. Scrolling turns into the wheel buttons X has always used, sideways too. In the virtual machine the mouse moves and the wheel scrolls. A real touchpad is next, on real hardware, which is where the rest of step 2 happens.
November 8, 2026, 4 pm
Compositing works, which is step 4. Windows can draw into pictures of their own, and a compositor puts them on the screen however it likes: with shadows, see-through, fading in and out. Below is xcompmgr, the small compositor from X.Org, drawing shadows under dwm's windows on X22, in the virtual machine.

XFree86 4.8 never had the Composite, Damage or XFixes extensions. X.Org added them in 2004, in X11R6.8, back when the two were still close, so we brought them over from there, along with the bits of the server underneath that they lean on. That also gives Present its missing XFixes.

Three old bugs turned up on the way: drawing through RENDER ignored "include child windows", a common way of painting drew nothing at all, and the test server couldn't make 8 or 32 bit pictures. And the server now draws into memory of its own and copies only what changed into the next frame, which is simpler than what XFree86 did and is what lets a compositor's drawing reach the screen.

November 8, 2026, 3 pm
The Present extension is in, which finishes step 3. With Present a program says "put this picture in my window at frame 1000" or "tell me when frame 1000 happens", and the server tells it back exactly when that was. It's how games, video players and GTK line their drawing up with the monitor instead of guessing.

XFree86 4.8 is older than Present, and also older than the kind of long event Present sends, so both had to be written from nothing, about 600 lines. The frame counter comes from the kernel. QEMU's virtual card doesn't have one, so there the server keeps a 60 Hz clock itself, and that's what we could test today: 60 frames took 1.000 seconds, and 20 pictures asked for 20 frames in a row went up on 20 frames in a row. The kernel's counter gets its first real test on real hardware.

Not there yet: updating just part of a window (that needs the XFixes extension, which XFree86 also doesn't have), fences, and handing a whole-screen window straight to the monitor without a copy. Those come with steps 4 and 5.

November 8, 2026, 2:50 pm
Three smaller things. UK keyboards work (X22_KEYMAP=gb), and other layouts are a few lines each. When the screensaver says so, the monitor now really switches off, through the kernel, instead of showing black. And the server has the extensions a desktop expects back: XFree86's small server left out SYNC, DPMS, the screen saver extension, double buffering, RECORD, X-Resource and Xinerama to stay small. GTK times its frames with SYNC, so that one matters for step 3.
November 8, 2026, 2:35 pm
No more tearing. X22 now keeps two buffers: the monitor shows one while the next frame is drawn into the other, and the kernel swaps them at the moment the screen starts a new refresh (a page flip). Until it says the swap happened, new drawing waits for the next frame. So the screen never shows half a frame, and nothing is drawn faster than the monitor can show it. That's the heart of step 3. The other half, letting programs know when their frame was shown (the Present extension), comes next.
November 8, 2026, 1:50 pm
The code is on GitHub: tortr-rs/x22. Also new: keyboards come straight from the kernel's input devices now, with the Super key working, which XFree86's small server never saw. dwm is all Super, so that mattered. There was one bug: the first key combo after starting did nothing. The mic mute key's number was one past the end of the server's key table, and writing it there marked Super as already held down, so the first real press looked like key repeat and got dropped. Fixed the same afternoon.
November 8, 2026, 1:25 pm
Real screens! Well, a real screen in a virtual machine, but it's the same road a real graphics card takes.

XFree86 4.8 came with a small server called Xfbdev, which draws on /dev/fb0. We tried it, and found out most Linux kernels don't make /dev/fb0 any more. So we taught it the way kernels do screens now, kernel mode-setting: it opens /dev/dri/card0, finds the monitor, asks for its best mode, and puts a buffer on it. Drawing happens in ordinary memory, and only the boxes that changed get copied over and reported to the kernel. That's about 300 lines, and it's the first half of step 2.

The test boots this computer's own kernel in QEMU with nothing in it but our server, dwm and three windows, and takes a picture of the screen. Next: input through libinput instead of the old console drivers, then real hardware.

November 8, 2026, 1:10 pm
It runs! Xvfb builds on GCC 16, and our dwm runs on it, with the gaps, the bar and the wallpaper, the same setup as on our own desktop. Step 1 is done.

The first bug was a funny one: dwm's amber came out blue. XFree86's Xvfb puts red in the low byte of each pixel and blue in the high one, the opposite of what everything since expects, so every color made from the server's masks came out backwards. Three lines to fix, an hour to find.

November 8, 2026, 3 am
Day one. XFree86 4.8.0 is in our repo, untouched, as the first commit. The first build on a 2026 compiler is running: 2008 C doesn't go through GCC 16 without some convincing. The first goal is small on purpose: build Xvfb, the X server that draws into memory instead of a screen, and run dwm on it. Our dwm is in the same repo.

Making X smooth

When people say Wayland is smoother, they're mostly right about today's X servers, and very right about XFree86, which is older than all of it. Here's what's missing and what we're going to do about it, roughly in order:

StepWhatWhy it matters
1Builds and runs on Linux today. Xvfb first, with dwm on it.Nothing else can happen until it runs. Done November 8.
2Real screens through the kernel. Kernel mode-setting (KMS) for every graphics card, and libinput for keyboards, mice and touchpads.XFree86's drivers program the graphics chip themselves, the 2008 way. Today the kernel does that, for every card, and does it right. Doing this now: screens and keyboards work in a virtual machine, and mice and touchpads go through libinput. Real hardware is next.
3Every frame on time. Page flips that wait for the screen's refresh, so nothing ever tears, and the Present extension so programs know when their frame was shown.This is most of what "smooth" means. Tearing is the thing people notice first. Done November 8, in a virtual machine. Real hardware still has to say so.
4Compositing. The Composite and Damage extensions.XFree86 4.8 has neither. Without them there are no compositors, no shadows, no smooth window effects. Done November 8, in a virtual machine, with xcompmgr.
5Drawing on the GPU. OpenGL-backed 2D drawing and DRI3, so programs and games render straight on the graphics card.Faster drawing, and the same path games and browsers expect.
6Today's screens. Plugging monitors in and out, several monitors, HiDPI, 144 Hz and up, variable refresh.All newer than XFree86.
7Security. Going through every X security fix since 2008 and applying the ones that apply to us.X has had a lot of them. A server can't be shipped until this is done. Done for the server and the font library November 10. One fix from June is left.
8Proof. Frame timing and input latency, measured against X.Org and Wayland on the same computer, published here."As smooth as Wayland" is a claim. We'll show the numbers, good or bad.

Questions

Why fork XFree86 and not X.Org?

X.Org is XFree86 continued, with eighteen years of work on top, and it's what Chamesle runs today. We wanted to start from the X we remember and build it back up ourselves, knowing every piece we add and why. It's the harder way. It's also the way you learn how all of it works.

Will my programs work on it?

That's the whole idea. Anything that runs on X should run on X22, back to programs from the 80s. Programs that only speak Wayland won't, the same as on any X server.

When can I use it?

No date. When it's good enough to replace X.Org on your computer, it becomes an option in Jiggity, and after that, maybe the default. Not before it's passed step 7.

Where's the code?

On GitHub: github.com/tortr-rs/x22. The first commit is XFree86 4.8.0 exactly as released, and everything after it is ours, so git log tells the whole story. The README says how to build it and run it, and test/vm boots it in QEMU if you want to see it on a screen without touching your own X.
